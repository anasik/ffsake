# Local attach acceptance — 2026-10-29

On macOS 27.0 ARM64, the existing MIT-licensed Samsung netcoredbg 3.2.0-1 (release 3.2.0-1092, `9744e1f`; release ZIP SHA-256 `f4fa33b3ff874910cc184b4bb3b9c56d0abdf5c6521cee0b144d7c6e4a6e59ea`) attached to a separately started, disposable .NET 8 process through FFSAKE MCP. The host-controlled adapter configuration selected the `processId` argument; the MCP attach request exposed the configuration name and explicit PID. This was a direct MCP exercise, not an agent or interactive host-approval test.

The actual trace shows an invalid PID rejected, a source breakpoint stop, an authorized `Program.Main` stack frame, and local integer `count` observed as `26`. FFSAKE performed step-in, step-out, step-over, continue and pause, and rejected an old frame handle after resumption. The independent target was alive after detach and after MCP server exit, before the test explicitly terminated it. [Full tool-call trace](trace.json) records returned values and timing; transient paths and PIDs are specific to that run. The test exercises the workflow, not universal adapter correctness.

Reproduce with the [debugging instructions](../../DEBUGGING.md#reproduce). `scripts/debug_attach_smoke.py` creates and builds its own target and takes the separately installed adapter path. On Linux its disposable target opts itself into ptrace attachment with `PR_SET_PTRACER_ANY`; it does not change system-wide ptrace policy. `scripts/debug_attach_protocol_smoke.py` uses a controlled fake DAP peer, not a debugger, to test cancellation, MCP EOF, session expiry, unsupported capability, request timeout, `terminateDebuggee=false`, target survival and owned adapter/descendant cleanup. Existing launch regression remains a real netcoredbg test. Host-specific normal approval for the new tool was tested as generated configuration, not with a fresh interactive agent prompt.

The installed Apple Command Line Tools `lldb-dap` reported version `lldb-1700.0.9.46` in a direct DAP probe, then emitted a crash-report request during attachment to a disposable C target and disconnected before completing. The target remained alive after adapter exit. This is not a successful LLDB attach and does not establish the cause. It is not part of the netcoredbg MCP test.
